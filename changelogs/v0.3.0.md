# v0.3.0

Plugins are now loaded from the plugin directory at startup. Adding a plugin no
longer means rebuilding the proxy.

## Plugin loader

- **`plugin.Loader`** opens every `.so` file in `plugins/` when the proxy starts.
  A plugin is a `main` package built with `go build -buildmode=plugin` that calls
  `plugin.Register` from an `init` function. Exporting a `New` function or a
  `Plugin` variable works too.
- **Failures are explained, not dumped.** The loader turns Go's runtime errors
  into the fix: a proxy built without cgo, a plugin built for another platform,
  or one built against a different Vortex version each get a message saying what
  to do. A file that fails to open is skipped and the proxy still starts.
- **Plugins compiled into the binary keep working** and run side by side with
  the loaded ones.

## What Go requires

Loading plugins is only possible under conditions Go imposes:

- The proxy must be built with `CGO_ENABLED=1`. The Linux release builds,
  `make build` and `start.sh` now do.
- Linux or macOS only — Go cannot load plugins on Windows.
- The plugin must be built with the same Go toolchain and against the same
  Vortex version, so plugins have to be rebuilt whenever the proxy is updated.
- Plugins cannot be unloaded: changing one means restarting the proxy. Use
  `plugins.disabled` to keep one from loading.

## Changed

- Linux release builds are now dynamically linked (cgo) so they can load
  plugins. The Windows and macOS builds stay static and cannot.
- `make build` builds with cgo enabled; `make plugin DIR=...` and `make plugins`
  build plugin files.
- `start.sh` builds the proxy with cgo and rebuilds any plugin whose sources sit
  in `plugins/src/<name>/` before starting.
- The example plugin is a `main` package, loadable as a file.

## Added

- `plugin/loadtest`, which builds the example plugin and loads it, so the loader
  is covered by the test suite.
- Build and install section in the plugin documentation.
