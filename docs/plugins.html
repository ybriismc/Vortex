Plugin API

Vortex plugins are Go packages that subscribe to proxy events and act on the proxy through a small API. Drop the built plugin in the plugins/ directory and the proxy loads it on the next start — no rebuild of the proxy, no imports to edit. This page covers building, the lifecycle, every event the proxy fires and every function a plugin can call.

package plugin package event loaded at startup

The model

A plugin is a Go main package built with go build -buildmode=plugin, which produces a .so file. Put that file in the proxy's plugin directory and Vortex opens it at startup: the plugin's init registers it, and from there it behaves like any other plugin.

plugins/ bans.so ← built with -buildmode=plugin, loaded at startup bans/ ← the plugin's own directory, created for it config.yml greeter.so greeter/ config.yml

Adding, updating or removing a plugin is a file operation plus a restart of the proxy.

What Go requires

Go's plugin support is real but strict. These are hard requirements, not recommendations:

RequirementWhy, and what happens otherwise
The proxy must be built with CGO_ENABLED=1 A static binary cannot load plugins. Otherwise every plugin fails with plugin: not implemented. The official Linux release builds and make build already enable it.
Linux or macOS Go cannot load plugins on Windows at all. On Windows, compile the plugin into the binary instead.
Same Go toolchain as the proxy The runtime refuses a plugin built with a different Go version.
Same version of every shared dependency The plugin and the proxy share vortex/plugin, vortex/event, Spectrum and gophertunnel. A mismatch fails with "different version of package". Build plugins from the Vortex source tree of the version you run.
Same OS and architecture A plugin is native code: no cross loading.
In practice this means rebuild your plugins whenever you update Vortex. The loader reports each of these cases with the fix instead of the raw runtime error, and a plugin that fails to open is skipped — the proxy and the other plugins still start.

Plugins cannot be unloaded

Go never unloads a plugin, so there is no reload or runtime disable: changing a plugin means restarting the proxy. To keep a plugin from loading without deleting its file, list its name under plugins.disabled in config.yml.

The alternative: compiling a plugin in

The same code also works compiled into the binary — rename the package from main to the plugin's name and import it from cmd/vortex. That drops every requirement above (it works on Windows, needs no cgo) at the cost of rebuilding the proxy to change a plugin. Both kinds run side by side.

Your first plugin

Create a main package, for example under plugins/src/welcome/ in your Vortex checkout:

package main

import (
    "fmt"

    "github.com/ybriismc/vortex/event"
    "github.com/ybriismc/vortex/plugin"
)

func init() { plugin.Register(&Welcome{}) }

// main is never called: a plugin is loaded, not executed. It exists so the
// package also builds with "go build ./...".
func main() {}

type Welcome struct {
    plugin.Base // no-op Enable and Disable

    proxy plugin.Proxy
}

func (*Welcome) Manifest() plugin.Manifest {
    return plugin.Manifest{
        Name:        "welcome",
        Version:     "1.0.0",
        Author:      "you",
        Description: "Greets players when they join.",
    }
}

func (w *Welcome) Load(ctx *plugin.Context) error {
    event.Subscribe(ctx.Bus(), func(e *event.PlayerJoin) {
        name := e.Session.Client().IdentityData().DisplayName
        ctx.Logger().Info("player joined", "username", name, "server", e.Addr)
        w.proxy.Broadcast(fmt.Sprintf("§e%v joined!", name))
    }, event.Normal)
    return nil
}

func (w *Welcome) Enable(proxy plugin.Proxy) error {
    w.proxy = proxy
    return nil
}

A complete, working example lives in examples/plugins/greeter.

Build and install

Build the plugin into the proxy's plugin directory and restart the proxy:

go build -buildmode=plugin -o plugins/welcome.so ./plugins/src/welcome

The Makefile wraps that, and also builds every example at once:

make plugin DIR=./plugins/src/welcome    # one plugin
make plugin DIR=./examples/plugins/greeter NAME=greeter
make plugins                            # every example plugin

./start.sh goes one step further on private hosts: any plugin whose sources sit in plugins/src/<name>/ is rebuilt automatically before the proxy starts, so updating a plugin is editing its code and restarting.

On startup the proxy reports what it loaded:

level=INFO msg="loaded plugin" plugin=welcome version=1.0.0
level=INFO msg="enabled plugins" count=1 plugins="welcome 1.0.0"

How a plugin announces itself

Calling plugin.Register from init is the way to do it. For cases where that does not fit, the loader also accepts an exported symbol — the first one it finds wins:

SymbolDeclaration
init + Registerfunc init() { plugin.Register(&Welcome{}) }
Newfunc New() plugin.Plugin { return &Welcome{} }
Pluginvar Plugin = &Welcome{}

A file that offers none of them is reported and skipped.

Lifecycle

The Plugin interface has four methods, three of which run in a fixed order:

MethodWhenWhat belongs here
Manifest() ManifestAt registrationName, version, author, description, dependencies
Load(*Context) errorBefore the listener startsSubscribe to events, read configuration, open databases
Enable(Proxy) errorOnce the proxy is listeningStore the Proxy, start background work
Disable() errorOn shutdown, reverse orderFlush files, close connections

The split matters: subscriptions have to exist before the proxy is built, because Vortex decides which packets to decode from what the plugins listen for. Embed plugin.Base to get no-op Enable and Disable.

Dependencies

Manifest.Depends names plugins that must load first. Vortex sorts plugins so dependencies load and enable before their dependents, and disables them in reverse order. A plugin whose dependency is missing is skipped with a warning — as is every plugin depending on it. A dependency cycle stops the proxy with an error.

A plugin can be turned off without recompiling through plugins.disabled in config.yml.

Configuration and files

Each plugin owns a directory under plugins.directory, named after it. Context.Config reads config.yml from it — and, when the file does not exist yet, writes the defaults you passed in, so the first run seeds the file: 

type Config struct {
    Welcome string   `yaml:"welcome"`
    Admins  []string `yaml:"admins"`
}

func (w *Welcome) Load(ctx *plugin.Context) error {
    w.conf = Config{Welcome: "§eWelcome, %v!"} // defaults
    if err := ctx.Config(&w.conf); err != nil {
        return err
    }
    ...
}
FunctionDescription
ctx.Manifest()The plugin's own manifest
ctx.Bus()The event bus, tagged with the plugin's name
ctx.Logger()A *slog.Logger tagged with the plugin's name
ctx.Dir()The plugin's directory, created on demand
ctx.Config(v)Reads config.yml into v, seeding it on the first run
ctx.SaveConfig(v)Writes v back to config.yml

Returning an error from Load skips the plugin; the proxy keeps running.

Event bus

Three generic functions, and that is the whole API:

event.Subscribe(bus, func(e *event.PlayerJoin) { ... }, event.Normal)
event.Call(bus, &event.PlayerJoin{...})   // fired by the proxy
event.Subscribed[event.Chat](bus)         // does anything listen?

Priorities

Handlers run from Lowest to Monitor; handlers of the same priority run in subscription order. Put decisions early and observation late:

PriorityUse for
event.Lowest, event.LowDefaults another plugin may override
event.NormalOrdinary handlers
event.High, event.HighestDecisions that must win, such as a ban check
event.MonitorLogging and metrics — runs last and sees the final state

Cancelling

Events carrying event.Cancelling can be stopped with e.Cancel(). Every handler still runs after a cancellation — check e.Cancelled() if that matters to yours. What cancelling means depends on the event, and is documented per event below.

Panics

A handler that panics is logged with the plugin's name and the event type, and the remaining handlers still run. A broken plugin degrades one event instead of taking the proxy down.

Events

Every event lives in package event. Fields listed are the ones you act on.

Proxy

EventFiredFields
ProxyStartListener up, plugins enabledAddr
ProxyStopShutdown begins—

Player

EventFiredCancel meansFields
PlayerLogin Client identified itself, before the login sequence Reject the connection with Message Addr, Identity, Client, Message
PlayerJoin Player spawned on its first server — Session, Addr
PlayerQuit Player left the proxy — Session, Message

PlayerLogin is the cheapest place to refuse someone: no session exists yet and no server has been contacted. Identity holds the XUID, UUID and display name and is verified by Xbox Live; Client is sent by the client and can be forged.

Servers

EventFiredCancel meansFields
ServerSelect A server was picked, before dialing it Refuse the connection Conn, Addr (writable), Fallback
Transfer Before moving the player to another server Keep the player where it is Session, Origin, Target (writable), Fallback
TransferComplete Player connected to the new server — Session, Origin, Target, Fallback
TransferFailed The move failed; the player stays put — Session, Origin, Target, Fallback, Err

Fallback tells the two cases apart: a transfer requested by a server, and a fallback the proxy performs because the server the player was on died.

Chat and commands

EventFiredCancel meansFields
Chat Player sent a chat message Drop the message before the server sees it Session, Message (writable)
Command Player ran a command Handle it on the proxy; the server never sees it Session, Line (writable, no leading slash)
These two cost CPU. Vortex forwards client packets without decoding them — that is where its throughput comes from. Subscribing to Chat or Command makes the proxy decode text and command packets for every player. It only does so if something is actually subscribed, so do not subscribe "just in case".

Proxy functions

Enable hands the plugin a plugin.Proxy. Store it — it is the only way to act on the proxy from a handler.

Recipe: a proxy side command

Subscribe to Command, cancel the event, answer the player:

event.Subscribe(ctx.Bus(), func(e *event.Command) {
    fields := strings.Fields(e.Line)
    if len(fields) == 0 || !strings.EqualFold(fields[0], "hub") {
        return
    }

    e.Cancel() // the server never sees the command
    name := e.Session.Client().IdentityData().DisplayName
    if err := p.proxy.Transfer(name, "10.0.0.10:19133"); err != nil {
        _ = p.proxy.Message(name, "§cCould not send you to the hub.")
    }
}, event.Normal)
Bedrock caveat: the client only sends commands it knows about, from the command tree the server gave it. If no server registers /hub, the client refuses it locally and the proxy never sees it. Register the command on your servers (a no-op is enough — the proxy cancels it before it arrives), or trigger on a chat prefix through the Chat event instead, which always reaches the proxy.

Recipe: bans and whitelists

Do it in PlayerLogin, at event.High so it wins over other handlers. The player is rejected before a session exists: 

event.Subscribe(ctx.Bus(), func(e *event.PlayerLogin) {
    ban, ok := store.Lookup(e.Identity.XUID)
    if !ok {
        return
    }

    e.Message = "§cYou are banned: " + ban.Reason
    e.Cancel()
}, event.High)

To also drop a player already online when a ban lands, call proxy.Kick(username, reason). Key bans on Identity.XUID, not on the display name: names change, XUIDs do not.

Recipe: custom routing

ServerSelect runs after the balancer picked an address and lets you override it — per rank, per region, per queue, from your own database: 

event.Subscribe(ctx.Bus(), func(e *event.ServerSelect) {
    if e.Fallback {
        return // let the fallback pool do its job
    }

    if addr, ok := lobbyFor(e.Conn.IdentityData().XUID); ok {
        e.Addr = addr
    }
}, event.Normal)

The call is synchronous and blocking work is allowed here — Spectrum discovers servers asynchronously, one goroutine per login. Keep it bounded anyway: it sits in the login path.

Pitfalls

  • Do not block a handler for long. Transfer and chat events run on the session's own goroutine; a slow handler delays that player's packets. Hand slow work to a goroutine, or do it in ServerSelect, which is already off the hot path.
  • Handlers run concurrently across sessions. One goroutine per player means your shared state needs a mutex.
  • Store the Proxy in Enable, not in Load. It does not exist yet while plugins load.
  • Do not subscribe to Chat or Command unless you use them — each one turns on packet decoding for every player.
  • Trust Identity, not Client. Client data is whatever the player's client claims.
